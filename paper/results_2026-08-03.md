# Validation checkpoint — 2026-08-03

First end-to-end validation score for the hard-cutover pipeline. Every previous
all-relations number in this repository belongs to the retired GPT-OSS-20B
prototype.

## Setup

- Model: `google/gemma-3-27b-it` (27.4B total, inside the 32B limit)
- Inference: OpenRouter, provider pinned to DeepInfra, no fallbacks
- Configuration: `configs/improvement-plan.yaml`, output mode `prompt_json`
- Predictions: `data/model_outputs/val-merged.jsonl` (478 rows)

Hosted inference replaced local LM Studio, which measured ~0.8 tokens/second on
a Radeon 890M and put a full run at 4–14 days. The same run now costs
**$0.26 and about one hour**.

## What the experiments established

### Numeric sample count buys nothing beyond three samples

A train-only sweep over the 100 training `hasArea` rows compared six
aggregators at k in {3,5,7,10,15,20}. Accuracy was flat between 0.53 and 0.58
across the whole grid, non-monotonically, which at 100 rows is a two-to-three
row wobble. `hasArea` and `hasCapacity` were therefore cut from 20 and 15
samples to 7, removing about 1,600 calls per run at no measured cost.

### Selection cannot recover the numeric oracle gap

The correct area value appears somewhere among 20 samples for 73 of 100
validation rows, while the median returns 54. That gap is not recoverable:
mode-seeking, trimmed, and order-of-magnitude-filtered estimators all tied or
lost to the plain median on training data. When this model is wrong it is
consistently wrong, so the correct value is a minority answer that no
agreement-based rule can surface. This reproduces the conclusion the GPT-OSS
error analysis reached and shows it survives the model change.

Train and validation agree closely — median-at-20 scores 0.55 on train against
0.54 on validation, oracle 0.69 against 0.73 — which supports using training
traces to select aggregation settings.

### An omission pass must not run on an empty candidate set

Border precision collapsed to 0.779 in the first full run. In 12 of the 18
gold-empty rows every sample correctly returned no neighbours, and the
completion pass then invented maritime ones that verification accepted: Malta
gained Italy, Samoa gained American Samoa, Australia gained Papua New Guinea,
Indonesia and Timor-Leste. Across 68 rows the pass introduced 36 neighbours
while verification removed 22.

Asking "what is missing?" is a leading question, and a set with no members has
nothing missing from it. Skipping completion and verification on an empty
aggregate raised train borders to 0.889 and validation borders from 0.796 to
0.859.

### Raising the completion cap fixed award under-generation

Mean award prediction size rose from 15.2 to 152.7 against a gold mean of
145.8. The previous 2048-token cap truncated enumerations mid-object, and
because `extract_json_array` requires a syntactically complete array, a
truncated response yielded zero recipients rather than a partial list. Each
recipient also cost 23.3 tokens inside its `work`/`year` wrapper against 4.5 as
a bare string, for fields the pipeline discards on parse.

## Open regressions

`personHasCityOfDeath` and `countryLandBordersCountry` both moved the same way:
recall up, precision down. Death recall rose from 0.480 to 0.630 while
precision fell to 0.370, and it now predicts empty on 13 rows against 39
gold-empty. Borders predicts empty on 10 rows against 18.

Two causes are confounded and have not been separated. Demonstration selection
was changed to mirror the training empty rate rather than the previous fixed
60% empty mix, which moved both relations along the precision/recall curve; and
the model changed at the same time. Neither relation's thresholds have ever
been calibrated — `abstention_thresholds` still carries its starting values of
0.50.

The next experiments should therefore generate train-only traces for
`personHasCityOfDeath` and `companyTradesAtStockExchange`, run
`akbc.py calibrate`, and lock the result before another validation run. Borders
has no support threshold at all and aggregates by pure union, so one
hallucinating sample of three is enough to lose a gold-empty row.

## Model comparison: Gemma 4 31B

A second complete validation run used `google/gemma-4-31b-it` (30.7B dense,
inside the 32B limit) under an identical configuration, served by CoreWeave at
bf16 for all 5,392 calls. Cost $0.3724.

| Relation | Gemma 4 31B | Gemma 3 27B | Delta | Reference |
|---|---:|---:|---:|---:|
| `countryLandBordersCountry` | 0.989 | 0.859 | +0.130 | 0.991 |
| `personHasCityOfDeath` | 0.460 | 0.340 | +0.120 | 0.620 |
| `companyTradesAtStockExchange` | 0.713 | 0.648 | +0.064 | 0.770 |
| `hasCapacity` | 0.220 | 0.230 | -0.010 | 0.290 |
| `awardWonBy` | 0.148 | 0.205 | -0.057 | 0.234 |
| `hasArea` | 0.370 | 0.520 | -0.150 | 0.730 |
| **All relations** | **0.513** | 0.490 | +0.022 | 0.650 |

The models are complementary rather than ordered. Gemma 4 is better on every
relation that rewards following a precise definition — borders reach 0.989
against a reference of 0.991, and the remaining error is a single row — while
Gemma 3 is better on the two relations that reward raw numeric recall. Because
27.4B and 30.7B sum to 58.1B, the challenge's parameter rule forbids combining
them, so the complementarity cannot be exploited and one model must be chosen.

Two confounds are unresolved. The numeric sample count of 7 was selected from
Gemma 3 training traces and has never been validated for Gemma 4, so part of
the `hasArea` regression may be a mis-set sample count rather than weaker
recall. Gemma 4 also exposes a configurable reasoning mode that this
configuration does not set explicitly.

### Provider routing is a required control, not a detail

OpenRouter serves this model from fp4 through bf16 depending on backend.
Pinning precision alone still routed a run to a JAX-backed provider that
rejects `seed` outright, which killed a validation run at row 100 after
exhausting every retry. Runs now pin provider and precision together and record
the serving provider on every call. Comparing two models across different
quantizations would confound the comparison this table is meant to support.
